Brainfuck as a ROP Compiler: Turning Programs into Return Chains

There is something deeply cursed about using ret as an execution engine.

Normally, Return-Oriented Programming (ROP) is treated as an exploitation technique: find gadgets, chain them together, bypass NX, spawn a shell, done.

But after playing with weird machines for a while, I started asking a different question:

What if ROP is not just an exploitation trick?

What if it is an actual compilation target?

That idea eventually turned into a tiny experiment:

Brainfuck → ROP chain → execution via ret

No dispatcher loop.

No instruction decoder.

No normal control flow.

Just stack manipulation and ret.

The result was a surprisingly functional stack-driven virtual machine.

The Core Idea

Traditional interpreters usually look like this:

fetch → decode → execute

Mine does not.

Instead, a Brainfuck program is translated directly into a sequence of gadget addresses:

[g_add][g_add][g_inc_ptr][g_write]...

The stack itself becomes the instruction stream.

Execution starts like this:

lea rsp, chain
ret

That single ret starts the entire program.

From that point onward, execution proceeds entirely through chained returns:

ret → gadget
ret → gadget
ret → gadget

At this point, rsp effectively becomes the program counter.

The Runtime

The VM itself is tiny.

Each Brainfuck instruction maps to a small gadget:

+  → increment byte
-  → decrement byte
>  → increment pointer
<  → decrement pointer
.  → write syscall
,  → read syscall

Minimal gadgets look like this:

g_add:
    inc byte ptr [rbx]
    ret

g_inc_ptr:
    inc rbx
    ret

Every gadget ends with ret, which keeps the chain alive.

No Dispatcher

The weird part is that there is no central execution loop.

No:

while (...) {
    switch(opcode) {

Nothing like that exists.

The stack layout itself is the control flow.

That changes the entire execution model.

Loops Without Jumps

Brainfuck loops ([ and ]) turned out to be the most interesting part.

Normally, interpreters implement loops using jumps or branches.

I wanted to avoid that entirely.

Instead, loops are implemented by modifying rsp.

Forward skip:

cmp byte ptr [rbx], 0
jne continue
add rsp, N*8
continue:
    ret

Backward jump:

cmp byte ptr [rbx], 0
je continue
sub rsp, N*8
continue:
    ret

This means control flow emerges from stack arithmetic alone.

No dispatcher.

No instruction pointer.

No explicit jumps in the VM itself.

Just pointer movement.

The Compiler

The compiler is a small Python script that translates Brainfuck into ROP chains.

Example Brainfuck:

++++++++[>++++++++<-]>+.

Generated chain:

.quad g_add
.quad g_add
.quad g_add
...
.quad g_jz_skip_*
...
.quad g_jnz_back_*

The output is not bytecode.

It is already executable control flow.

Unexpected Bugs

One of the funniest bugs happened when the chain was placed in .data instead of .text.

The VM immediately exploded with:

SIGSEGV (SEGV_ACCERR)

because stack control flow eventually fell into non-executable memory.

Another annoying bug involved off-by-one errors in loop offsets.

Since ret implicitly advances rsp, all loop calculations had to account for stack movement that was not explicitly visible in the source.

A single wrong offset instantly destroyed execution.

Why This Felt Interesting

At some point I realized this stopped feeling like a Brainfuck interpreter.

What I accidentally built was closer to:

ROP as a target architecture

The compiled output is simultaneously:

  • a valid program
  • a valid ROP chain
  • a weird machine

That boundary gets blurry very quickly.

Final Thoughts

ROP is usually discussed as a constraint.

You are forced to reuse tiny instruction sequences because normal execution is unavailable.

This project flips that around.

Instead of treating ROP as a limitation, the entire system embraces it as the execution model itself.

The result is strange, fragile, slightly impractical, and honestly a lot more fun than I expected.

But it also raises an interesting question:

If a program and an exploit payload share the same underlying structure, where exactly is the line between them?

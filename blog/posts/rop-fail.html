Saat ROP Terlihat Benar Tapi Tetap Crash: Sebuah Kisah Debugging

Reverse engineering dan exploit development sering punya momen yang bikin frustasi: semuanya kelihatan benar, tapi program tetap segmentation fault.

Artikel ini membahas satu kasus sederhana: membangun ROP chain untuk melakukan write(1, "OK\n", 3), yang ternyata penuh jebakan kecil—mulai dari gadget yang "hampir benar", sampai asumsi yang salah tentang stack.

Setup: Minimal Target Binary

Kita mulai dengan binary sederhana berisi gadget manual:

pop rdi ; ret pop rsi ; ret pop rdx ; ret pop rax ; ret syscall ; ret

Gadget terakhir sengaja dibuat byte-level:

0f 05 ; syscall 
c3 ; ret

Agar benar-benar menjadi syscall ; ret

Tujuan

Kita ingin membuat ROP chain untuk:

write(1, "OK\n", 3) 
exit(0)

Secara teori, chain-nya sederhana:

pop rdi → 1 
pop rsi → &"OK\n" 
pop rdx → 3 
pop rax → 1 
syscall

pop rdi → 0 
pop rax → 60 
syscall

Problem #1: Gadget “Ada”, Tapi Tidak Bisa Dipakai

Awalnya, gadget yang ditemukan seperti ini:

pop rdi ; pop rsi ; pop rdx ; pop rax ; syscall

Sekilas terlihat powerful, tapi sebenarnya useless untuk ROP

Kenapa? karena tidak ada ret

Dalam ROP, setiap gadget harus mengembalikan kontrol ke stack. Tanpa ret, eksekusi akan lanjut ke memory berikutnya—bukan ke chain kita

Problem #2: syscall Tanpa ret

Kesalahan berikutnya lebih subtle, walaupun kita punya:

syscall

Nambahin ret di chain seperti ini:

syscall
ret

Gak akan bekerja

CPU tidak mengambil ret dari stack setelah syscall, dia melanjutkan eksekusi ke instruksi berikutnya di memory

Artinya:

Gadget harus benar-benar syscall ; ret di dalam binary,bukan disimulasikan dari chain

Problem #3: Tool Tidak Selalu Benar

Setelah memperbaiki binary, tool seperti ROPgadget masih menampilkan:

0x401009 : syscall
padahal disassembly menunjukkan: 

401009: 0f 05    syscall
40100b: c3       ret

Problem #4: Pointer yang "Kelihatan Benar"

Setelah gadget beres, chain tetap crash

Contoh:

rsi = BASE + 0x70

Data "OK\n" memang ada di offset 0x70, tapi tetap segfault

Problem #5: Stack Tidak Diam

Setiap gadget seperti: 

pop rdi
pop rsi
pop rdx
pop rax

menggeser rsp

Akibatnya, asumsi tentang layout memory menjadi salah

Yang terlihat benar di hexdump:

payload + 0x70 → "OK\n" tidak lagi valid saat runtime

Problem #6: ASLR

Lebih parah lagi, alamat mapping berubah setiap run:

mmap(...) = 0x7ffff7fb5000
mmap(...) = 0x7ffff7fae000

Artinya:

BASE + offset tidak bisa diandalkan tanpa leak

Turning Point

Solusi yang akhirnya stabil bukan memperbaiki offset, tapi mengubah pendekatan.

Alih-alih:

rsi = BASE + offset

kita gunakan:

rsi = rsp

Dengan menambahkan gadget:

mov rsi, rsp
ret

Final Working Idea

Dengan gadget tersebut:

pop rdi → 1
mov rsi, rsp
pop rdx → 3
pop rax → 1
syscall

Dan menaruh "OK\n" tepat setelah chain, pointer menjadi selalu valid—tanpa tergantung BASE, offset, atau ASLR

Key Lessons

  1. Gadget harus ret-terminated
  2. syscall tanpa ret memutus chain
  3. Tool bisa misleading
  4. Stack berubah setiap pop
  5. Hardcoded address rapuh
  6. RSP adalah sumber pointer paling stabil

Closing

Kasus ini terlihat sederhana:

hanya ingin print "OK\n"

Tapi di balik itu, ada banyak insight fundamental tentang bagaimana ROP benar-benar bekerja di level rendah

Yang menarik bukan hasil akhirnya, tapi proses debugging yang memaksa kita memahami:

Bagaimana CPU benar-benar mengeksekusi chain kita

Bonus

Eksperimen lanjutan:

  • Hilangkan gadget mov rsi, rsp
  • Coba buat self-locating ROP
  • Bangun interpreter kecil di atas ROP chain

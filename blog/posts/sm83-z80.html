Ketika Byte yang Sama Menjadi Dua Program Berbeda

Berawal dari postingan thread di X oleh Travis Goodspeed, jadi tertarik buat bahas ini

Jadi kuncinya SM83 bukan “Z80 kecil”, banyak opcode Z80 yang invalid di GameBoy, dan beberapa opcode GameBoy punya panjang instruksi beda dari Z80

Observer

Rule praktis yang kuat:

Disassemble dari offset entry pakai dua mode:
1. mode SM83
2. mode Z80

Lalu score:

SM83 kalau:
- banyak opcode SM83-only:
  08 10 22 2A 32 3A E0 E2 E8 EA F0 F2 F8 FA
- banyak akses FF00/FFxx I/O GameBoy
- tidak ada opcode invalid SM83 di jalur code

Z80 kalau:
- ada opcode Z80-only/prefix:
  DD FD ED
- ada IN/OUT:
  D3 DB
- ada EXX / EX DE,HL / shadow-register style:
  D9 E3 EB
- SM83 decoder ketemu banyak invalid opcode

Contoh itu giveaway banget:

31 fe ff    ld sp, $fffe
af          xor a
21 ff 9f    ld hl, $9fff
32          ld (hl-), a      ; SM83
cb 7c       bit 7, h
20 fb       jr nz, ...

Di Z80, byte 32 bukan ld (hl-),a, tapi:

32 cb 7c    ld ($7ccb), a

Jadi stream langsung geser alignment, lalu disassembly berikutnya jadi “masuk akal palsu” tapi sebenarnya salah.

Heuristic paling simpel:

SM83_INVALID = {
    0xD3, 0xDB, 0xDD, 0xE3, 0xE4, 0xEB,
    0xEC, 0xED, 0xF4, 0xFC, 0xFD
}

SM83_STRONG = {
    0x08, 0x10, 0x22, 0x2A, 0x32, 0x3A,
    0xE0, 0xE2, 0xE8, 0xEA, 0xF0, 0xF2,
    0xF8, 0xFA
}

Z80_STRONG = {
    0xDD, 0xFD, 0xED, 0xD3, 0xDB, 0xD9,
    0xE3, 0xEB
}

def classify(buf):
    sm83_score = 0
    z80_score = 0

    for b in buf:
        if b in SM83_INVALID:
            z80_score += 8

        if b in SM83_STRONG:
            sm83_score += 2

        if b in Z80_STRONG:
            z80_score += 6

    # GameBoy I/O style: FF00+n immediate ops
    for i in range(len(buf) - 1):
        if buf[i] in (0xE0, 0xF0):
            sm83_score += 6

    # classic SM83 pattern: ld (hl-),a ; cb-prefix op
    for i in range(len(buf) - 2):
        if buf[i] == 0x32 and buf[i + 1] == 0xCB:
            sm83_score += 10

    return "SM83/GameBoy" if sm83_score > z80_score else "Z80/TI"

Tapi versi yang bener-bener reliable jangan cuma scan byte mentah. Bikin recursive disassembler dari entry point, ikutin jr/jp/call/ret, lalu score hanya opcode yang benar-benar berada di jalur code.

Rule finalnya:

Kalau executed instruction stream mengandung DD/FD/ED/D3/DB → Z80.
Kalau executed instruction stream memakai 22/2A/32/3A/E0/F0/E2/F2/E8/F8
dan decoding Z80 bikin alignment/CFG aneh → SM83.

Puzzle ini kemungkinan besar solvable karena TI ROM Z80 pasti banyak IX/IY/ED/IO, sedangkan GameBoy code pasti banyak HL+/HL-/LDH FFxx.

#!/usr/bin/env python3
import sys
from collections import Counter

SM83_INVALID = {
    0xD3, 0xDB, 0xDD, 0xE3, 0xE4, 0xEB,
    0xEC, 0xED, 0xF4, 0xFC, 0xFD
}

SM83_STRONG = {
    0x08, 0x10, 0x22, 0x2A, 0x32, 0x3A,
    0xE0, 0xE2, 0xE8, 0xEA, 0xF0, 0xF2,
    0xF8, 0xFA
}

Z80_STRONG = {
    0xDD, 0xFD, 0xED, 0xD3, 0xDB, 0xD9,
    0xE3, 0xEB
}

def classify(buf):
    c = Counter(buf)

    sm83 = 0
    z80 = 0
    reasons = []

    for b in buf:
        if b in SM83_INVALID:
            z80 += 10
        if b in SM83_STRONG:
            sm83 += 3
        if b in Z80_STRONG:
            z80 += 8

    # GameBoy LDH: E0/F0 xx => [$FF00+n]
    ldh = sum(1 for i in range(len(buf)-1) if buf[i] in (0xE0, 0xF0))
    sm83 += ldh * 8
    if ldh:
        reasons.append(f"SM83 LDH patterns E0/F0: {ldh}")

    # GameBoy C-register I/O: E2/F2
    ldh_c = c[0xE2] + c[0xF2]
    sm83 += ldh_c * 8
    if ldh_c:
        reasons.append(f"SM83 LDH (C) patterns E2/F2: {ldh_c}")

    # GameBoy HL auto inc/dec opcodes
    hl_auto = c[0x22] + c[0x2A] + c[0x32] + c[0x3A]
    sm83 += hl_auto * 6
    if hl_auto:
        reasons.append(f"SM83 HL+/HL- patterns: {hl_auto}")

    # Z80 prefix families
    prefixes = c[0xDD] + c[0xFD] + c[0xED]
    z80 += prefixes * 15
    if prefixes:
        reasons.append(f"Z80 DD/FD/ED prefix usage: {prefixes}")

    # Z80 IN/OUT immediate
    io = c[0xD3] + c[0xDB]
    z80 += io * 15
    if io:
        reasons.append(f"Z80 IN/OUT opcodes D3/DB: {io}")

    # Very common GB startup pattern:
    # 31 FE FF AF 21 FF 9F 32 CB 7C 20 FB
    gb_bootish = bytes([0x31,0xFE,0xFF,0xAF,0x21,0xFF,0x9F,0x32,0xCB,0x7C,0x20,0xFB])
    if gb_bootish in buf:
        sm83 += 100
        reasons.append("GameBoy boot/init-like pattern found")

    verdict = "SM83 / GameBoy" if sm83 > z80 else "Z80 / TI calculator"

    return verdict, sm83, z80, reasons

def main():
    if len(sys.argv) != 2:
        print(f"usage: {sys.argv[0]} ")
        sys.exit(1)

    path = sys.argv[1]
    with open(path, "rb") as f:
        buf = f.read()

    # puzzle says 16KB executable code, but allow any size
    verdict, sm83, z80, reasons = classify(buf)

    print(f"[+] file       : {path}")
    print(f"[+] size       : {len(buf)} bytes")
    print(f"[+] SM83 score : {sm83}")
    print(f"[+] Z80 score  : {z80}")
    print(f"[+] verdict    : {verdict}")

    print("\n[+] reasons:")
    for r in reasons:
        print(f"    - {r}")

if __name__ == "__main__":
    main()

Let's dig!

Pertanyaannya:

Jika diberikan 16KB kode executable yang berasal dari Z80 atau SM83 (CPU Game Boy), bagaimana cara membedakannya?

Jawaban singkat dan terlihat mudah, Ya tinggal disassemble aja.

Masalahnya, SM83 dan Z80 punya hubungan yang cukup dekat. Banyak instruksi yang sama, register yang mirip, dan bytecode yang sering kali bisa diterjemahkan menjadi assembly yang terlihat valid di kedua arsitektur.

Kalau cuma diberi sekumpulan byte mentah tanpa informasi tambahan, ternyata membedakan keduanya tidak sesederhana yang dibayangkan.

Byte yang Sama, Assembly yang Berbeda

Misalkan kita memiliki byte berikut:

31 FE FF
AF
21 FF 9F
32
CB 7C
20 FB

Jika didisassemble sebagai SM83 (Game Boy), hasilnya:

ld sp,$fffe
xor a
ld hl,$9fff
ld (hl-),a
bit 7,h
jr nz,$0007

Kelihatannya masuk akal.

Sekarang coba decode byte yang sama sebagai Z80:

ld sp,$fffe
xor a
ld hl,$9fff
ld ($7ccb),a
jr nz,$0007

Di sini muncul perbedaan penting.

Opcode 0x32 pada SM83 berarti:

ld (hl-),a

Sedangkan pada Z80:

ld (nn),a

Instruksi yang tadinya hanya satu byte tiba-tiba dianggap sebagai instruksi tiga byte.

Akibatnya posisi decoding bergeser, dan seluruh disassembly setelahnya mulai kehilangan sinkronisasi.

Inilah petunjuk pertama yang menarik.

SM83 Bukan Z80 Mini

Banyak orang menganggap CPU Game Boy hanyalah Z80 yang dipangkas. Kenyataannya tidak sesederhana itu. Nintendo menghapus beberapa fitur Z80 dan menambahkan instruksi baru yang lebih cocok untuk kebutuhan Game Boy. Beberapa opcode khas Z80:

DD
FD
ED

D3
